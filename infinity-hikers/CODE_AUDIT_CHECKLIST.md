# Code Audit Checklist

Generated by a 5-way parallel audit (state/context layer, admin panel, hero/destination
pages, shared layout/routing, static/content pages). Each item has a concrete
`file:line` pointer and was verified by reading the actual code — nothing here is
speculative. Work through this in dependency-aware batches; check an item off only
after it's fixed **and** verified (see the audit-and-fix skill).

## Broken

- [ ] `src/context/ItineraryContext.jsx:183-185`, `TestimonialsContext.jsx:69`, `SettingsContext.jsx:52`, `SitePagesContext.jsx:124`, `PricingRulesContext.jsx:62`, `HeroContext.jsx:154` — every `reset*ToDefaults` only calls local `setState`, never writes the defaults back to Supabase; the "reset" silently reverts on the next fetch for any visitor (NavLinksContext/CatalogContext are the exception — they set `dirtyRef.current = true` so theirs actually persists).
- [ ] `src/context/ItineraryContext.jsx:126`, `TestimonialsContext.jsx:35`, `HeroContext.jsx:93`, `SettingsContext.jsx:37`, `SitePagesContext.jsx:94-100`, `PricingRulesContext.jsx:47` — the mount-time fetch's `.then()` unconditionally overwrites state with no check for whether a mutator already changed local state while the fetch was in flight; an edit made in that window gets clobbered by the stale GET response landing after it.
- [ ] `src/context/SettingsContext.jsx:43` and `PricingRulesContext.jsx:53` — `updateSettings`/`updateRules` build `next` off the closed-over state variable instead of a functional updater; two concurrent unawaited calls silently clobber each other (same bug class SitePagesContext worked around, not fixed here).
- [ ] `src/context/SitePagesContext.jsx:114` — `updatePage` itself still has the original stale-closure bug; `updatePages` was added as a workaround for batch callers but any caller using `updatePage` directly still hits it (file's own comment admits this).
- [ ] `src/context/NavLinksContext.jsx:63` and `CatalogContext.jsx:65` — when Supabase isn't configured, the debounced save silently no-ops (local state updates, nothing persists) with no error surfaced, unlike every other context which throws an explicit "Saving isn't set up yet" error.
- [ ] `src/pages/AdminPanel.jsx:221` (`openNewTour`) and `:228` (`openEditTour`) — neither resets `tourLocalPreviews`/`uploadingImages`/`tourUploadTokenRef`, unlike the hero form's `resetHeroUploadState()`; a stale preview/stuck "Uploading…" from one tour bleeds into the next tour's modal.
- [ ] `src/pages/AdminPanel.jsx:630` — `handleHeroSubmit` unconditionally refuses a past `dateStart`, with no carve-out for editing an existing already-past slide (the tour form has this via `tourMinDate` at `:822`); saving any unrelated edit on a past hero slide is blocked until the admin also fixes the date.
- [ ] `src/components/Preloader.jsx:98-104` — the cleanup for the inner `t2` timeout is `return`ed from inside the `setTimeout` callback instead of the `useEffect`; `setTimeout` discards that return value, so `t2` is never actually cleared.
- [ ] `src/components/Navbar.css:35-42` — `.navbar__logo-img` is 32×32px with `transform: scale(4)` applied; the layout box stays 32px while the visual renders at ~128px, causing it to overlap `.navbar__brand-text` and other navbar content.
- [ ] `src/components/CinematicHero.jsx:244-264` — the tagline block renders unconditionally (unlike the `slide.dates` block right above it, which is guarded); a slide with no tagline shows an empty italic line with just a lone blinking cursor.
- [ ] `src/pages/MapPage.jsx:62-66` — `FlyToMarker` calls `map.flyTo(...)` directly in the render body instead of inside a `useEffect`, violating render purity; can fire more than once as a side effect of rendering.

- [ ] `src/pages/AdminPanel.jsx:2181-2183` — testimonial "Rating" `<select>` is hardcoded to `[5,4,3]`; a testimonial with rating 1 or 2 (a valid stored value) has no matching option.
